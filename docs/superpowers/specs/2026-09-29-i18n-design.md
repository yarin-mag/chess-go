# Internationalization (i18n) — Design

B-Chess supports three languages: English (default, configurable), Hebrew, and Spanish. This covers every
piece of user-facing text in the app — static UI copy, and the generated prose (move descriptions, tutor
"why" explanations, weakness-dashboard insights) that today is built by string concatenation in plain
English. Opening names and puzzle position data (`assets/openings.json`, `assets/puzzles.json`) are **not**
translated — those are external chess data (ECO names, FEN positions), not authored UI text.

## Library & file layout

`react-i18next` (the standard React binding for i18next), added as a real dependency. Resource JSON lives
under `src/renderer/locales/<locale>/<namespace>.json`, one namespace per feature area so files stay
reviewable and translators can work on one area at a time:

```
src/renderer/locales/
  en/  common.json  game.json  tutor.json  stats.json  puzzles.json  online.json
  he/  (same six files)
  es/  (same six files)
```

- **common** — shared chrome: menu buttons, Settings panel, modals, generic actions (Undo, Flip, Menu…).
- **game** — everything from `features/game/labels.ts` (colorName, levelName, playerLabel,
  describeResult, DRAW_REASONS) and `core/describeMove.ts` (PIECE_NAMES, the move-description sentence
  builder), plus GameScreen/ControlBar/GameOverModal/ClockPanel copy.
- **tutor** — `engine/phrases.ts`'s PHRASES (short) and REASONS (long) tag-keyed templates, TutorPanel/
  ReasonModal copy.
- **stats** — `features/history/weaknessStats.ts`'s TAG_PHRASE map and `biggestWeakness()`'s sentence,
  plus the three independently-duplicated `TIER_LABEL` maps (TutorPanel, PuzzleScreen,
  WeaknessDashboardScreen — consolidated into one `stats.json` source during this migration) and
  `PHASE_LABEL`/`TAG_LABEL`.
- **puzzles** — `PuzzleMapScreen`'s `STAGE_THEME_LABEL` and any other puzzle-theme display text.
- **online** — OnlineLobbyScreen, ReactionPicker/ReactionBubble, SavedGamesScreen copy.

`src/renderer/i18n/index.ts` initializes i18next with these resources at app startup (imported once from
`main.tsx`), `react: { useSuspense: false }` (the app has no existing Suspense boundary, and the resources
are bundled at build time, not fetched — nothing to suspend on).

## Locale persistence & switching

`settingsStore` (already the home for `boardTheme` and other persisted preferences) gains a `locale: 'en' |
'he' | 'es'` field, defaulting to `'en'`, persisted the same way (zustand + `localStorage`, already the
established pattern in this codebase). A new "Language" `Segmented` control in `SettingsPanel` (mirrors the
existing board-theme picker exactly) calls `i18n.changeLanguage(locale)` alongside `settingsStore.update
({ locale })`, and a small effect at the app root syncs i18next's active language from the persisted
setting on load.

## RTL

Hebrew is right-to-left. A small effect (colocated with the locale-sync effect above) sets
`document.documentElement.dir = locale === 'he' ? 'rtl' : 'ltr'` whenever the locale changes. The chess
board must **never** mirror — that's the existing, unrelated "⇅ Flip" feature (`gameStore.flipped`) — so
`Board.module.css`'s root rule gets an explicit `direction: ltr` to opt the board out of the document-wide
`dir="rtl"` regardless of locale. Everything else (menus, buttons, sidebars, modals) mirrors normally, which
is what `dir="rtl"` is for.

## Reactions: wire key vs. display text

`REACTIONS: readonly string[]` today conflates two things that must split apart: the value sent over the
peer connection and validated by `isKnownReaction`, and the text shown on screen. Once display text is
translated, two players with different locales must each see a reaction in **their own** language, not
whatever the sender's client happened to render — so the wire value becomes a stable, language-independent
**key**, and display text becomes a locale lookup on the *receiving* client.

```ts
// features/online/protocol.ts
export const REACTION_KEYS = [
  'thumbsUp', 'wow', 'yikes', 'fire', 'handshake', 'laugh', 'pawn',
  'niceMove', 'wowText', 'blunder', 'brilliant', 'check', 'goodGame', 'oops', 'wellPlayed',
] as const;
export type ReactionKey = (typeof REACTION_KEYS)[number];

export type NetworkMessage =
  | ...
  | { type: 'reaction'; key: ReactionKey }; // was `text: string`

export function isKnownReaction(key: string): key is ReactionKey {
  return (REACTION_KEYS as readonly string[]).includes(key);
}
```

`online.json`'s `reactions` object maps each key to its display string (the emoji ones are identical across
locales — `👍`, `😮`, etc. — only the text presets differ: `"niceMove": "Nice move!"` / `"תזוזה יפה!"` /
`"¡Buena jugada!"`). `ReactionPicker` renders `t(`reactions.${key}`)` as each button's label instead of the
key itself; `onlineStore.sendReaction`/`useOnlineSync`'s receive path carry `key` instead of `text`;
`reactionStore.show`/`ReactionBubble` render the *looked-up* text, not the raw key, so the bubble always
reflects the viewer's own locale even when the sender used a different one.

## Fallback behavior

i18next's built-in fallback (`fallbackLng: 'en'`) handles a missing key in `he`/`es` transparently — the
English string renders instead of a blank or a raw key. This matters in practice: Hebrew and Spanish
resource files can land incrementally (or a future fourth language can start as an empty file) without ever
showing broken UI.

## Testing approach

Pure-function modules that move under i18n (`describeMove`, `phraseFor`/`reasonFor`, `weaknessStats`'s
`biggestWeakness`) keep their existing unit tests, adapted to call through a `t`-like function rather than
returning hardcoded English — each gets one additional test asserting the *shape* of interpolation (that
`{{square}}`/`{{piece}}` placeholders are actually substituted), not exhaustive per-locale prose assertions
(translation quality isn't something a unit test can grade). Component-level i18n wiring (`useTranslation`
calls, the `<Trans>`/`t()` swaps in JSX) has no dedicated tests, matching this codebase's existing
convention that pure UI wiring is verified by typecheck + build, not unit tests.

## Non-goals

- Translating `assets/openings.json` (ECO opening names) or puzzle position/theme *data* (only the
  human-authored theme *labels* in `puzzles.json` are translated, not the puzzle content itself).
- A language picker on first launch / browser-language auto-detection — the default is always English,
  changed explicitly in Settings.
- Any fourth language. The locale type is a closed union (`'en' | 'he' | 'es'`), not an open string, so
  adding one later is a deliberate, typed change, not a data-only addition.
